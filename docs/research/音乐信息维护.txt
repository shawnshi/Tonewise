基于上述边界，PC 端可将这五项能力整合为一套统一的“双轨治理 + 置信度暂存审校 + 分层落盘”架构：SVG一、五项新增功能的具体工程实现设计
1. 专辑封面自动获取（三级瀑布源 + 目录级省空间存储）
多源检索瀑布：优先用已匹配的 Release MBID 请求 Cover Art Archive API 获取社区校对的 front-1200 原盘正封；未命中（尤其是华语与日系原声专辑）时，分区域（country=cn / jp / us）轮询 iTunes Search Artwork 接口，将返回缩略图地址替换为未压缩原图路径拉取 1200×1200 至 3000×3000 高清正方图；最后以 Last.fm album.getInfo 兜底。图像质检与落盘规范：自动剔除分辨率低于 600×600 或宽高比偏差超过 5% 的拉伸图。落盘采用“同专辑目录存单份 cover.jpg 为主、单曲可选内嵌 600×600 为辅”——避免一张 12 首歌的无损专辑重复内嵌 12 份大图导致体积暴涨并撑爆 8KB FLAC Padding 块，同时目录级 cover.jpg 可被手机端 OxygenCobalt/Auxio 直接读取。
2. 专辑、Artist、Composer、Conductor 简介获取（Wikidata 图谱桥接 + 旁路缓存库）跨角色多源抓取：流行歌手与常规专辑直接调取 Last.fm artist.getInfo 与 album.getInfo 的 Wiki 摘要；针对 Last.fm 极度匮乏的作曲家（Composer）与指挥家（Conductor），通过 MusicBrainz API（携带 inc=url-rels）提取人物关联的 Wikidata QID（遵循 MusicBrainz-Wikidata 链接规范），再按 zh-hans → zh-hant（自动转简） → en 顺序拉取维基百科 REST Summary 首段小传与生卒年属性（纯英文条目可在 PC 端经本地/云端 LLM 接口一次性译制为 200 字客观中文卡片）。严禁写入音频头：长文本简介绝不塞入音频文件的 COMMENT 标签（否则会显著拖慢双端扫描速度），统一存入 /Music/.tonewise/encyclopedia.db（SQLite 独立表，以规范化人名/专辑名 + MBID 为主键），随双端同步静默下发手机离线展示。
3. 残缺 Genre 与五维扩展标签补全（本地 Essentia ONNX 多头推理 + 规则推导）
依托桌面 CPU（AVX2）或核显 DirectML 运行开源音频分析框架 Essentia 预训练 ONNX 模型组（单曲推理仅需 0.15–0.3 秒，零 API 费用且不受外网限流影响），以 discogs-effnet 200 维声学嵌入为共享骨干，逐项补齐缺失字段（详见下表参数映射）：DJ_SCENE 采用确定性后置推导而非黑盒盲猜：模型负责客观听感（人声、能量、BPM、情绪），而 DJ_SCENE 通过可配置的规则矩阵由前四项确定性映射生成（例如：DJ_VOCALS=instrumental 且 DJ_ENERGY=low 且 Mood 属于静谧簇 → 自动赋予 focus;relax），保证打标逻辑与你手工策展习惯完全自洽。
4. 残缺 Album、Year、Publisher 补全（声学指纹 + 首发原盘消歧）
两级防污染识别：先调用 Chromaprint (fpcalc) 生成音频前 120 秒声学指纹，经 AcoustID 接口 换取准确的 MusicBrainz Recording MBID（即使文件名是乱码也能认出原曲）。同目录聚类与原盘优先：若同一文件夹下多首曲目共同指向某张专辑则直接锁定该发行版；若是散装单曲，则在关联的候选列表中强制按 Release-Group Primary Type = Album + Official + 最早发行日筛选原始录音室专辑（主动过滤 Various Artists 拼盘精选集），将 Release-Group 首发年写入 Year / ORIGINALDATE，将唱片厂牌写入 Publisher（对应 ID3v2 TPUB / Vorbis LABEL）。补全目标字段容器底层标签帧（Picard 规范）主力信源或本地推理模型自动入库置信度与映射阈值DJ_VOCALSTXXX:DJ_VOCALS / Vorbis DJ_VOCALSEssentia voice_instrumental-discogs-effnetP_inst 高于 0.80 判 instrumental；低于 0.25 判 vocal；中间区间进人工复核TempoTBPM + Vorbis TEMPOEssentia TempoCNN 瞬态节拍提取器置信度高于 0.75 自动写入精确 BPM 并按 40–240 五档阈值映射 Slow 至 Very FastDJ_ENERGY & MoodTXXX:DJ_ENERGY + TMOO / MOODarousal-valence 回归头 + mood_* 四分类头 + LUFS唤醒度三分位映射 low / medium / high；情绪最高分头超 0.65 映射至 Calm / Chill / Cheerful 等词表GenreTCON / Vorbis GENREMusicBrainz 高票 Tag + genre_discogs400 融合400 类细粒度风格（如 Fingerstyle）经本地字典归口至你的顶层流派（如 Acoustic）Album / Year / PublisherTALB、TDRC/TDOR、TPUB/LABELfpcalc → AcoustID → MusicBrainz Release-Group指纹匹配分高于 0.88 且时长误差在 ±3 秒 内进绿色待提交池，否则进双栏对比审校台
5. 与 Last.fm 双向同步播放记录与 Play Count（非对称高水位账本模型）
为在不违背 Last.fm 14 天时间窗口限制的前提下实现零丢数体验，PC 端维护一套三向核对账本：下行全量拉取（Cloud → PC）：通过 user.getRecentTracks（按上次同步的 from 时间戳增量翻页）拉回你在其他设备（如流媒体、旧手机）产生的所有完播流水写入 history.jsonl，并结合 artist.getCorrection 别名表与忽略大小写归并匹配本地曲目（同时调用 user.getLovedTracks 双向实时同步红心收藏，红心接口无 14 天限制）。上行近 14 天补交（PC & Android → Cloud）：筛选本地与手机端同步回来的 history.jsonl 中尚未标记 lastfm_synced、且播放时间在 14 天窗口内的完播事件，按每批最多 50 条调用 track.scrobble 批量上推；上报前按 (规范艺人, 规范曲名, 时间戳 ±120秒) 与云端已拉取流水做幂等比对，彻底杜绝与手机端 Pano Scrobbler 重复记账。Play Count 高水位线融合计算：对每首曲目保留导入时的历史离线基数 legacy_count（如 MusicBee 既有播放次数），本地最终生效的播放总次数按 max(legacy_count, lastfm_pulled_count) + local_unsynced_expired_count 动态合成——既让新产生的每一次播放双端与云端完全同步，又完整保住早年超 14 天无法上推的本地历史播放数。
二、防止“自动毁库”的两条铁律
严格“只补空缺（Fill-Missing Only）”默认策略：扫描器仅读取并填充当前为空白的字段（例如你截图中 75% 空白的 Tempo 或缺失的 Publisher），你手工打好标的 DJ_SCENE 与 Mood 默认加锁保护，绝不允许模型静默篡改。
暂存对比台（Staging Diff Queue）先审后写：所有在线抓回的专辑/厂牌与本地模型推理出的五维标签先写入临时表，界面高亮显示“原值（空）→ 建议值 + 置信度评分”，确认无误后通过 TagLib 2.3.2 事务批量写回音频头，并支持按批次一键撤销回滚。
